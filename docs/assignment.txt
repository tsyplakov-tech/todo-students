Итоговое практическое задание на 24.10.2026 • Индивидуальная работа
1. Результат работы
Создайте приложение на Node.js и Express: список дел, добавление, изменение названия, отметка
выполнения и удаление. Предоставьте работающий HTTPS-адрес. Интерфейс может быть на обычном
HTML/JavaScript; отдельный фронтенд-фреймворк не требуется.
Выберите PostgreSQL, MySQL/MariaDB или MongoDB. Другую СУБД согласуйте до реализации. Все дела
хранятся в БД; изменения сохраняются после перезапуска приложения. Зависимости для работы с
выбранной БД разрешены.
2. Данные и персонализация
Таблица или коллекция tasks содержит: id (уникальный UUID-строка), ownerLogin (логин Moodle), title
(строка), done (логическое значение), runId (строка), createdAt (время создания). API возвращает эти поля с
указанными именами; createdAt - строка UTC в ISO 8601. Сопоставление с физическими столбцами опишите
в README. Дополнительный внутренний ключ БД допустим.
Сервер задает id, ownerLogin, createdAt и начальное done=false. ФИО и логин берутся из вашего профиля
Moodle, задаются в конфигурации и не принимаются из тела запросов. GET /api/author/ возвращает
{"login":"...","fullName":"..."}. После входа с токеном интерфейс показывает эти сведения. Вручную создайте
в БД через приложение дело «Итоговая работа 24.10.2026: <логин Moodle>» с runId="manual".
3. Обязательный HTTP-интерфейс
 Запрос
Требование
GET /login/
200; логин Moodle, Content-Type: text/plain. Доступен без токена.
GET /api/author/
200; JSON с login и fullName.
POST /api/tasks/
JSON: title, runId. Ответ 201 и созданное дело.
GET /api/tasks/?runId=…
200; JSON-массив дел автора с этим runId; пустой результат - [].
GET /api/tasks/:id/
200 и дело; отсутствующее дело - 404.
PATCH /api/tasks/:id/
JSON: title и/или done. Ответ 200 и обновленное дело; отсутствующее -
404.
DELETE /api/tasks/:id/
204 без тела; отсутствующее дело - 404.
Все /api/ требуют Authorization: Bearer <токен>; без правильного токена - 401. Все ответы API с телом имеют тип
application/json. Токен передавайте серверу из интерфейса, не встраивайте его в исходники. Все маршруты выше
оканчиваются «/».
title: после trim от 1 до 200 символов; runId: 1-64 символа из A-Z, a-z, 0-9, «_», «-»; done - только boolean. POST допускает
только title и runId, PATCH - непустой набор title/done. Ошибочный JSON, неверные типы, лишние поля, неверный UUID
или отсутствие runId в списке - 400. Ошибка БД - 503. Ошибки: {"error":"краткое описание"}.

4. Краткий анализ размещения БД
Сравните три варианта: хотя бы один отечественный сервис и один вариант без оплаты студентом.
Рассмотрите факультетский Helios: проверьте наличие доступа, доступную СУБД, ограничения и
возможность подключения вашего приложения. Helios не обязателен для развертывания; отсутствие доступа
зафиксируйте.
Для каждого варианта укажите СУБД, бесплатный тариф / пробный период / оплату, ограничения хранения
и подключения, результат собственной проверки доступности, официальный источник и дату проверки.
Постоянный бесплатный тариф и временный грант различайте. Платные услуги приобретать не требуется.
Возможные отправные точки: Timeweb Cloud, MongoDB Atlas, Supabase, факультетский Helios. Выбор не
ограничивается этим списком. Условия и доступность проверьте на дату выполнения работы.
5. Проверяемость и доступ
Выделите отдельную учебную таблицу/коллекцию tasks. Обеспечьте проверяющему независимое
подключение к этой же БД с чтением, добавлением, изменением и удалением только учебных данных;
допустим согласованный ограниченный SSH-туннель. Приложение должно возвращать актуальные данные
БД. Скриншот, дамп или дополнительный HTTP-маршрут приложения не заменяет доступ к БД.
Доступ к API и БД передайте преподавателю личным сообщением в Moodle; в теме отметьте, что он
отправлен. Используйте отдельные ограниченные учетные данные. Не передавайте пароль от Moodle, ИСУ
или основного аккаунта Helios. Если площадка не позволяет выделить требуемый доступ, выберите другую
либо согласуйте способ доступа до реализации.
6. Что сдать в форуме
Каждый студент создает одну свою тему с названием «Логин Moodle - ФИО». Исправления и ответы
размещайте репликами в этой теме.
В первом сообщении: HTTPS-адрес приложения; логин и ФИО; выбранные СУБД и площадка; ссылка на
репозиторий с точным commit или ZIP исходников; README. Приложите package.json, lock-файл,
.env.example без секретов и SQL-схему/миграцию либо описание структуры коллекции и ее инициализации.
README: 300-450 слов плюс таблицы и команды. Включите сравнение трех вариантов размещения,
обоснование выбора и структуры приложения, схему данных/сопоставление полей, версии Node.js и СУБД,
команды установки, инициализации и запуска. Приложение должно быть доступно на время проверки;
действующие токены и строки подключения публично не размещайте.
